## 通信链路与延迟优化

### 功能描述

手柄输入从 Xbox 手柄经电脑端桥接程序，通过 USB CDC 虚拟串口发送给 STM32。固件解析帧、检查链路状态并更新舵机目标。目标是让机械臂对手柄操作及时响应，并在通信中断时安全停止。

### 方案选型与原因

- **传输方式：USB CDC 虚拟串口**。原因：不需要 UART 转接板，减少接线；直接复用 Blue Pill 的 USB 口供电和通信，便于串口监视器调试。
- **帧格式：换行分隔的 ASCII 文本帧**。原因：人眼可读，串口调试时可以直接看到每一帧的内容，不需要专用解析工具。
- **安全机制：链路建立后必须回中并松开所有动作输入才解锁**。原因：避免上电或重连时舵机和底盘因残留输入而突然动作。通信超时（250ms）后自动锁定并停止底盘。

### 迭代过程

#### 第一阶段：舵机调度周期（35ms → 20ms）

- **问题**：早期固件的舵机调度周期为 35ms，机械臂从手柄输入到开始动作的反应偏慢。
- **尝试**：把 `SERVO_STEP_MS` 从 35ms 改为 20ms，与 SG90 常见的 50Hz（20ms）刷新周期对齐。
- **失败原因**：周期缩短后，串口回传 ACK 的频率随之增加。早期版本每次变化都回传，串口写入一度出现压力。
- **定位与修正**：ACK 改为只在关节目标变化时回传，且每 100ms 最多回传一次。
- **结论**：舵机调度为 20ms，ACK 限频。

#### 第二阶段：桥接发送节奏

- **问题**：早期桥接程序循环中有控制台 `print` 调用，并且在无输入时依赖 100ms 的兜底发送，松手后可能停留在旧状态。
- **尝试**：删除循环内的 `print`，主循环等待缩短为 5ms，发送间隔上限为 20ms，输入变化时立即发送。
- **结论**：桥接发送间隔上限为 20ms，主循环等待 5ms。
- **未完成的测量**：用户主观反馈延迟从"约 3 秒"降到"跟手"，但没有 RTT 或视频数帧的测量数据，因此没有可写入的毫秒级结果。早期的"约 0.3~0.5 秒"和"约 3 秒"出自不同时期、语境不同，无法合并为同一个数值。

#### 第三阶段：右摇杆幅度编码错误

- **问题**：早期桥接只发送 `-1 / 0 / +1` 方向量，固件用整数计算比例时，例如 `15 * 1 / 100` 结果为 0，联动几乎不动。
- **尝试**：桥接改为发送 `-100..100` 的百分比幅度，死区外的幅度保留。
- **结论**：幅度编码修正。此后的右摇杆 Y 联动已在 [03 大小臂联动](03-大小臂联动.md) 中被替换，但编码问题的修正经验保留在这里。

#### 第四阶段：手柄断开与串口超时

- **问题**：测试中桥接程序出现以下情况：
  - 第一次启动：找到手柄后，第一帧写入时报 `Write timeout`，程序退出。
  - 第二次和第三次启动：pygame 报告未检测到手柄，但 Windows 设备管理器中 `Xbox Wireless Controller` 状态正常。
  - 第五次启动（拆除胶带后）：再次报 `Write timeout`，随后 COM6 从系统中消失。
- **尝试**：
  1. 用中立帧单独测试固件，固件能正常建立链路并返回 ACK，说明固件和串口在该时段可用。
  2. 检查进程列表，确认桥接程序的运行状态。
  3. 查看 Windows 的 PnP 设备列表，确认 STM32 USB 设备是否存在。
- **失败原因**：
  - `Write timeout` 的根因尚未确认。
  - pygame 找不到手柄的根因尚未确认，可能与蓝牙手柄的休眠或连接状态有关。
  - COM6 消失时，Windows 中已无 STM32 的 USB 设备记录。原因未确认，可能是 USB 线或接口接触不良，也可能是舵机供电波动导致 Blue Pill 复位或掉电。
- **定位与修正**：本阶段尚未修正。已确定的事实是：固件在桥接停止后，250ms 内会锁定并停止底盘，舵机保持最后位置。
- **结论**：通信链路在本次测试中不稳定，这是下一步必须排查的问题，见 [05 开发环境与调试流程](05-开发环境与调试流程.md)。

### 当前状态与遗留问题

- 固件 ACK、超时锁定和中立解锁已通过串口验证。
- 延迟的 RTT 或数帧测量：未测量。目前只有操作手的主观反馈（感觉"跟手"），没有可写入的数据。
- `Write timeout` 和 STM32 USB 掉线的原因：未确认。
- 桥接程序 `joystick.init()` 的弃用警告不影响功能，后续应改为无需重复初始化的写法。
